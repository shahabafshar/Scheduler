# Real-Time WAN Traffic Models and Shaping

## Real-Time Communications Overview

### Network Model
```
Source -----> [Network] -----> Destination
```

### Performance Metrics

1. **Bandwidth** of the connection
2. **End-to-end delay**: The total time the packet experienced from source to destination
3. **Delay jitter**: Maximum variation in delay experienced by packets that travel across the connection
   - Delay-jitter = Max_delay – Min_delay
4. **Packet Loss**: Percentage of packets lost

---

## Applications and Guarantee Requirements

### Interactive Applications
- **Require:** Bound on both delay and delay-jitter
- **Can tolerate:** Occasional message loss
- **Examples:** Continuous media traffic (video or audio playback)

### Discrete Applications
- **Require:** Error-free service
- **Can tolerate:** Both delay and jitter
- **Examples:** File transfer, Image retrieval

---

## Approaches to Real-Time Communication

### Pure Circuit Switching
- Reserves the entire physical/virtual channel for the connection
- Example: Telephone networks

### Pure Packet Switching
- Can efficiently utilize network bandwidth but cannot provide real-time guarantees
- Example: Internet

### Packet-Oriented Switching
- A virtual channel is established before transmission begins
- Employs statistical multiplexing to utilize bandwidth efficiently
- Example: ATM (Asynchronous Transfer Mode) network

---

## Types of Service

### Guaranteed Service
- **Deterministic or hard guaranteed service**
- Conservative in resource reservation (for peak workload)
- Simplest method for real-time services

### Predictive Service
- Meant for adaptive applications that can tolerate occasional violation of delay bound
- Multimedia playback applications function well with this category

### As-Soon-As-Possible Service
- Best-effort service with priorities
- Highest priority to interactive burst traffic
- Lowest to asynchronous bulk transfer
- Provides no guarantees, and no resources are reserved

---

## Real-Time Channel

### Definition
A **virtual circuit** that provides the required end-to-end QoS guarantees.

**QoS parameters:** Bandwidth, delay, delay jitter, packet loss, etc.

### Life-Cycle of a Real-Time Channel

1. **Channel Establishment Phase**
   - QoS routing
   - Resource reservation

2. **Data Transmission Phase**
   - Traffic policing/shaping
   - Packet scheduling
   - Rate adaptation

3. **Channel Tear-Down Phase**
   - Releasing session resources

---

## Characterization of Real-Time Traffic

### Constant Bit Rate (CBR)

- Fixed-size packets generated at **regular intervals**
- Smooth and **nonbursty**
- Example: Data generated by sensors (periodic)

### Variable Bit Rate (VBR)

Two types:
1. **Fixed-sized packets** arriving at irregular intervals
2. **Variable-sized packets** arriving at regular intervals

Examples:
- Voice traffic (talk spurts alternate with periods of silence)
- Video source (different compression ratios result in variable size packets generated at regular intervals)

### Traffic Characteristics Change

Even **CBR traffic becomes bursty** when passing through switches due to cross traffic.

## Traffic Models

### Peak-Rate Model

Most hard real-time systems use the peak-rate model for traffic characterization.

**Parameters** for a connection i:
- **Minimum inter-arrival time** between messages (Tᵢ)
- **Maximum message rate** (1 / Tᵢ)
- **Maximum message length** (μᵢ)
- **End-to-end delay bound** (Dᵢ)

**Peak bandwidth requirement:**
**μᵢ / Tᵢ**

**Properties:**
- The peak-rate model is exact only for CBR traffic
- **Overstates the bandwidth requirement** for all VBR sources

#### CBR Example
```
Min inter-arrival time Tᵢ = 6 sec
Max message rate = 1/6 = 0.16 message/sec
Max message length μᵢ = 1 kbits
Bandwidth required = 1/6 = 0.16 kbits/sec (exact)
```

#### VBR Example
```
Min inter-arrival time Tᵢ = 2 sec
Max message rate = 0.5 messages/sec
Max message length μᵢ = 3 Kbits
Peak bandwidth required = 3/2 = 1.5 Kbits/sec
```
**Result:** An overstatement of the B/W requirement

---

## Linear Bounded Arrival Process (LBAP) Model

### Key Innovation
Uses an **additional parameter** representing the **maximum burst size (Bᵢ)**

### Bounding Formula
In this model, the number of bits transmitted during any interval of length t is bounded by:

**Bᵢ + (t / Tᵢ) × μᵢ**

### Properties
- This model can **guarantee deterministic delay bounds**
- Better than peak-rate model for VBR traffic
- Still an overestimate but more accurate than peak-rate

### LBAP Example
```
Average inter-arrival time Tᵢ = 6 sec
Max message rate = 0.16 messages/sec
Burst size Bᵢ = 1 Kbits
Max message length μᵢ = 3 Kbits
Bandwidth required = 3/6 + 1 = 1.5 Kbits/sec
```

**Result:** An overestimate of the B/W requirement, but better than peak model

## Traffic Shaping/Policing

### Regulating Flow Control

- The **bursty traffic** in the network results in congestion
- Traffic shaping **reduces congestion** and thus helps the carrier live up to its guarantees
- Traffic shaping is about regulating the **average rate (and burstiness)** of data transmission

### Traffic Shaping Definition
- Traffic shaping controls the **rate** at which packets are sent (not just how many)
- At connection set-up time, the sender and carrier negotiate a **traffic pattern (shape)**
- Two main algorithms: **Leaky Bucket** and **Token Bucket**

---

## Leaky Bucket Algorithm

### How It Works
- Implemented as a **single-server queue with constant service time**
- If the bucket (buffer) overflows then **packets are discarded**
- The leaky bucket **enforces a constant output rate** regardless of the burstiness of the input
- Does nothing when input is idle

### Operation
- The host injects **one packet per clock tick** onto the network
- Results in a **uniform flow of packets**, smoothing out bursts and reducing congestion
- When packets are the same size (as in ATM cells), one packet per tick is okay
- For variable length packets, it is better to allow a **fixed number of bytes per tick**

---

## Token Bucket Algorithm

### How It Works
- In contrast to LB, the Token Bucket (TB) algorithm allows the **output rate to vary**, depending on the size of the burst
- The bucket holds **tokens**. To transmit a packet, the host must **capture and destroy one token**
- Tokens are generated by a clock at the rate of **one token every Δt sec**
- **Idle hosts** can capture and save up tokens (up to the max. size of the bucket) in order to send larger bursts later

### Operation
- TB accumulates fixed size tokens in a token bucket
- Transmits a packet (from data buffer, if any are there) or arriving packet if the sum of the token sizes in the bucket add up to packet size
- More tokens are **periodically added** to the bucket (at rate Δt)
- If tokens are to be added when the bucket is full, they are **discarded**

### Properties
- Does **not bound the peak rate** of small bursts, because bucket may contain enough token to cover a complete burst size
- Performance depends only on the **sum of the data buffer size and the token bucket size**

### Token Bucket Example
- **2 tokens** of size **100 bytes** added each second
- Token bucket of **capacity 500 bytes**
- **Avg. rate** = 200 bytes/sec
- **Burst size** = 500 bytes
- Packets bigger than 500 bytes will never be sent
- **Peak rate is unbounded** – i.e., 500 bytes of burst can be transmitted arbitrarily fast

---

## Leaky Bucket vs. Token Bucket

| Aspect | Leaky Bucket | Token Bucket |
|--------|-------------|--------------|
| **What is discarded** | Packets | Tokens |
| **Constant output rate** | Yes | No (varies) |
| **Saving capacity** | No | Yes |
| **Burst handling** | Smooths all bursts | Allows some bursts |
| **Output behavior** | Sends packets at average rate | Allows faster output for bursts |
| **Use case** | Constant rate guarantees | Flexible rate with burst allowance |

---

## Summary

### Traffic Models
- **Peak-Rate Model**: Conservative, simple, overstates requirements for VBR
- **LBAP Model**: More accurate, includes burst parameter, still bounded

### Shaping Algorithms
- **Leaky Bucket**: Constant output rate, no burst capability, discards packets
- **Token Bucket**: Variable output rate, burst capability, discards tokens, more flexible
